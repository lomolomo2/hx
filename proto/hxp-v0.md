# hxp v0 -- the hx engine protocol

> host (TypeScript) <-> hxd (the native C++ engine), JSONL over stdio.
> **This document precedes the implementation. Where any implementation
> disagrees with it, the implementation is what changes.**

## 0. Transport

- One JSON object per line, UTF-8, `\n`-separated; **no bare newline may
  appear inside a line**.
- host -> hxd goes to hxd's stdin; hxd -> host goes over stdout.
- hxd's stderr carries human-readable diagnostics only and **takes no part in
  the protocol**.
- Per-line cap `8 MiB`; past it hxd replies `E_LINE_TOO_LONG` and discards that
  line (the connection is not dropped).

## 1. The three message types

| Type | How it is identified | Direction |
|---|---|---|
| Request | has `id` and `op` | host -> hxd |
| Reply | has `reply_to` | hxd -> host |
| Event | has `event`, no `reply_to` | hxd -> host |

### Request

```jsonc
{
  "id": "r1",              // generated by the host, unique, correlates the reply
  "op": "exec.start",      // operation name
  "args": { },             // operation-specific
  "replay": "never"        // optional: "never" | "safe", default "never"
}
```

`replay` is **crash-recovery semantics**, not a retry policy:
- `safe` -- the operation has no external side effects or is idempotent
  (reading a file, querying state), so it is safe to re-run during recovery
- `never` -- it has irreversible side effects (writing a file, running a
  command), so during recovery it **must never be re-run**; the interruption
  can only be reported

### Reply

```jsonc
{"reply_to":"r1","ok":true,"result":{ }}
{"reply_to":"r1","ok":false,"error":{"code":"E_PATH_ESCAPE","message":"...","detail":{ }}}
```

**Every Request receives exactly one Reply.** Intermediate output from a long
task goes through Events, never through Replies.

### Event

```jsonc
{"event":"exec.output","cell":"c1","stream":"stdout","data":"..."}
```

## 2. Error codes

| code | Meaning |
|---|---|
| `E_BAD_REQUEST` | Malformed JSON structure / a missing field |
| `E_UNKNOWN_OP` | Unknown op |
| `E_BAD_ARGS` | args do not satisfy that op's schema |
| `E_PATH_ESCAPE` | After realpath, the path is not inside the workspace roots |
| `E_DENIED` | Refused by the sandbox or by policy |
| `E_NO_SESSION` | No `session.open` yet |
| `E_NO_CELL` | The cell does not exist or has been reaped |
| `E_LINE_TOO_LONG` | A line exceeded the cap |
| `E_SANDBOX_UNAVAILABLE` | The required isolation layer is unavailable on this kernel |
| `E_INTERNAL` | An internal engine error (should be accompanied by a stderr log) |

## 3. Operations

### 3.1 `ping` -- liveness probe
`args`: none · `result`: `{"pong":true,"pid":<int>}`

### 3.2 `selftest` -- capability self-test
`args`: none
`result`:
```jsonc
{
  "kernel": "7.0.0-28-generic",
  "landlock": {"available": true, "abi": 6, "fs": true, "net": true},
  "seccomp": {"available": true},
  "userns":  {"available": true},
  "cgroup2": {"available": true, "path": "/sys/fs/cgroup"}
}
```
**Purpose**: the host calls it once at startup and writes the result into the
rollout's `session_meta` -- so that reading the log later tells you whether
that run actually had a sandbox.

### 3.3 `session.open` -- open a session and **fix** the policy
```jsonc
{"op":"session.open","args":{
  "roots": ["/abs/path/to/workspace"],   // absolute, stored after realpath
  "sandbox": "workspace-write",          // read-only | workspace-write | danger-full-access
  "net": "deny",                         // deny | allow
  "extra_read_paths": ["/sys/fs/cgroup"] // extra read-only grants; see below
}}
```
`result`: `{"session":"s1","effective":{...}}` -- `effective` is the policy
**actually in force**.
If `net:deny` was requested but the kernel's Landlock ABI is < 4,
`effective.net` is `"allow"` with `warnings:[...]` attached.
**The engine never pretends to have done what it could not do.**

`extra_read_paths` supplements the default system read-only paths. The default
set is deliberately narrow (excluding `$HOME` and `/sys/fs/cgroup`), but some
tasks genuinely need an opening: a toolchain installed in `$HOME`
(nvm/rustup/conda), or a task that is itself about some system interface.
**An explicit grant beats widening the defaults.**
A non-existent path is skipped and listed honestly in `effective`, rather than
being allowed to stop the session from opening.

> **Policy tightens monotonically**: after `session.open`, a session's policy
> can only become stricter, never looser (Landlock itself is irrevocable). The
> only way to loosen it is to open a new session.

### 3.4 `exec.start` -- start a process inside the sandbox
```jsonc
{"op":"exec.start","args":{
  "cmd": ["bash","-lc","npm test"],
  "cwd": ".",                 // relative to roots[0], validated by path_guard
  "env": {"CI":"1"},          // allow-listed and merged into the minimal environment; the host's full env is not inherited
  "timeout_ms": 600000,
  "pty": false,               // true goes through forkpty, so REPLs and interactive commands work
  "rows": 24, "cols": 120     // meaningful only in pty mode
}}
```
`result`: `{"cell":"c1","pty":false}` -- **`cell` is an opaque ID; a real pid
appears nowhere in the protocol.**

In pty mode the output does not distinguish stdout from stderr (a terminal has
only one stream to begin with), and the `stream` field of `exec.output` is
`"pty"`.

### 3.5 `exec.stdin` -- feed input to an existing cell
`args`: `{"cell":"c1","data":"y\n","close":false}`
`result`: `{"written":2,"pending":0}`

`pending > 0` means the kernel buffer filled and only part went in -- the
caller decides whether to retry the remainder.
`close:true` closes stdin (sending EOF to things like `cat`); it has no effect
in pty mode, where reading and writing share one fd.

### 3.6 `exec.wait` -- collect output with a timeout
```jsonc
{"op":"exec.wait","args":{"cell":"c1","yield_ms":1000,"max_bytes":16384}}
```
`result`: `{"done":false,"data":"...","truncated":true,"exit_code":null}`

**Return rather than keep waiting**, handing whatever partial output there is
to the caller (the counterpart of `KeWaitForSingleObject` with a timeout).
When `done:true`, `exit_code` is non-null and that cell is reaped immediately
afterwards.

### 3.7 `exec.kill`
`args`: `{"cell":"c1","signal":"TERM"}` · `result`: `{"killed":true}`

### 3.8 `fs.read`
`args`: `{"path":"src/a.ts","offset":0,"limit":500}` (counted in **lines**)
`result`: `{"content":"...","lines":123,"truncated":false}`

### 3.9 `fs.apply_patch`
`args`: `{"patch":"*** Update File: src/a.ts\n@@ ...\n"}`
`result`: `{"changes":[{"path":"src/a.ts","kind":"update"}]}`
**Atomicity**: either all of it succeeds or nothing reaches the disk (tmp +
rename). A failure must never leave half a file behind.

### 3.10 `fs.stat` / `fs.glob`
`fs.stat` args `{"path":"..."}` · `fs.glob` args
`{"pattern":"src/**/*.ts","limit":1000}`

### 3.11 `log.append` -- durable rollout append
`args`: `{"record":{ }}` · `result`: `{"seq":42}`
The engine guarantees: **either the whole line is written or nothing is**
(the complete line is assembled before `write`, with `fsync` where necessary).
A host crash does not affect a log already on disk.

### 3.12 `policy.set` -- tighten the policy
`args`: `{"sandbox":"read-only"}` or `{"net":"deny"}` · `result`:
`{"effective":{...}}`
Only **stricter** values are accepted; an attempt to loosen returns `E_DENIED`.

## 4. Events

| event | Fields | When |
|---|---|---|
| `exec.output` | `cell,stream,data` | The child produced output. `stream` is `stdout` / `stderr` / `pty` |
| `exec.exit` | `cell,exit_code,signal` | The child ended |
| `policy.violation` | `op,path/target,reason` | An operation was refused by the sandbox or path_guard |
| `engine.warning` | `message,detail` | Running degraded (e.g. an insufficient Landlock ABI) |

`policy.violation` **must emit both an event and an error reply**: the reply is
for the caller, the event is for auditing and the UI (rule one: the two streams
stay separate).

## 5. Parameter capture (a normative requirement)

On receiving a Request, the engine **must** process it in this order, with no
reordering:

1. Read the whole line and parse it as JSON (failure -> `E_BAD_REQUEST`)
2. Validate `args` against that op's schema (failure -> `E_BAD_ARGS`)
3. **Copy args into the engine's own memory**, and refer to the parse buffer no
   further
4. Put every path parameter through `path_guard` (realpath + roots validation)
5. Execute

Step 3 is the key defence against double-fetch: **the value that was validated
and the value that is used must be the same memory.**

## 6. Versioning

The handshake is carried by `selftest`'s `result.proto` field:
`{"proto":"hxp/0"}`.
v0 makes no backward-compatibility guarantee; the host and hxd must be built
from the same version.
